ReconcileRuntime 做了好多事

```go
func (r *RuntimeReconciler) ReconcileRuntime(engine base.Engine, ctx cruntime.ReconcileRequestContext) (result ctrl.Result, err error) {
	// 1.创建各自runtime对应的工作负载，通过helm渲染
	if !utils.IsSetupDone(ctx.Dataset) {
		ready, err := engine.Setup(ctx)
	}
	// 2.创建fluid类型的卷

	// 3.sync up
```

#### pod使用fuse卷，触发节点打标，创建fuse-pod

在csi的NodeStageVolume阶段，给node打label，ds感知到label后在节点上创建fuse-pod。

同理在NodeUnstageVolume阶段，这个label会被移除，fuse-pod会被销毁。


注意销毁fuse-pod时，存在clean-policy，默认policy是`OnRuntimeDeletedCleanPolicy`，默认不会走到移除label的阶段。

是通过删除runtime时，顺带删除了ds，才再删除的fuse-pod

```go
	
	func (ns *nodeServer) NodeUnstageVolume(ctx context.Context, req *csi.NodeUnstageVolumeRequest) (*csi.NodeUnstageVolumeResponse, error) {
	cleanPolicy := runtimeInfo.GetFuseCleanPolicy()
	glog.Infof("NodeUnstageVolume: Using %s clean policy for runtime %s in namespace %s", cleanPolicy, runtimeInfo.GetName(), runtimeInfo.GetNamespace())
	switch cleanPolicy {
	case v1alpha1.OnDemandCleanPolicy:
		shouldCleanFuse = true
	case v1alpha1.OnRuntimeDeletedCleanPolicy:
		shouldCleanFuse = false
	default:
		return nil, errors.Errorf("NodeUnstageVolume: unknown Fuse clean policy: %s", cleanPolicy)
	}

	if !shouldCleanFuse {
		return &csi.NodeUnstageVolumeResponse{}, nil
	}
```

```sh
# Sends a signal to each of the running background processes
#
# Args:
#     1: the signal to send
function forward_signal {
  local signal="${1}"
  # background jobs don't respond to SIGINT (2)
  # Change to SIGHUP (1)
  if [ "${signal}" -eq "2" ]; then
    signal="1"
  fi

  local procs="$(jobs -p)"
  echo -e "Forwarding signal ${signal} to processes:\n${procs}"
  while read -r proc; do
    if [ -n "${proc}" ]; then
      kill -${signal} "${proc}"
    fi
  done <<< "${procs}"
  # This function may take over execution thread from the "main" function.
  # Wait if the processes are still up. Additional signals of the same type as this
  # will not be able to be processed
  wait
}

# Sets up traps on all signals [1, 31]
#
# Notes about trapping some signals
# - SIGINT (2): Background process (started with &) ignore SIGINT. As a workaround to still
#               terminate processes when SIGINT is passed, convert the signal sent to the
#               processes to be something other than SIGINT
# - SIGKILL (9): Cannot be trapped. It will directly kill the bash parent shell, the child
#                processes will continue to live
function setup_signals {
  for i in {1..31}; do
    trap "forward_signal ${i}" ${i}
  done

  # If the script exits for any reason without a signal, forward a SIGHUP to the children
  trap "forward_signal 1" EXIT
}

        useradd -u ${ALLUXIO_UID} -g ${ALLUXIO_GROUP} ${ALLUXIO_USERNAME}

      usermod -a -G root ${ALLUXIO_USERNAME}
      mkdir -p /journal
```

#### fuse-pod生命周期

1. 容器挂载fuse卷，调度到节点后，触发csi接口 NodeStageVolume ，会给节点打标，打标后ds开始干活创建fuse-pod
2. 当节点上没有使用fuse卷的pod，触发csi接口 NodeUnStageVolume，该阶段会判断fuse-clean-policy，当policy为`OnRuntimeDeletedCleanPolicy`，无事发生。当policy为`OnDemandCleanPolicy`，会主动移除labe，ds开始干活删除fuse-pod。默认不删除fuse-pod，一旦节点上存在过fuse-pod，会一直存在，直到runtime被删除。

## 双栈适配

### 背景

1. master启动时存在一个就绪探针，其中是一个mount脚本，这个脚本必需被执行，切脚本依赖环境变量ALLUXIO_MASTER_HOSTNAME来获取master地址。
2. 我们无法在pod中直接注入一个环境变量为ipv4地址。
3. 如果ALLUXIO_MASTER_HOSTNAME不存在，则脚本和主程序都会使用svc dns来获得master地址



### 修改entrypoint.sh 脚本

entrypoint.sh 脚本位于 alluxio-runtime 镜像中，该脚本由alluxio官方固化到镜像中。**修改该脚本需要 alluxio-runtime重新出镜像。**

alluxio-runtime-master 、alluxio-runtime-worker 、alluxio-runtime-fuse 等alluxio相关pod均使用同一镜像，容器启动时均执行entrypoint.sh 脚本，根据容器环境变量的不同，创建不同角色的java进程


`alluxio fsadmin report` 命令来获取alluxio缓存信息



由于kubectl exec 创建新的终端后，环境变量信息难以获取，因此上述脚本无法将alluxio-runtime-master 的IPV4地址持久化。

因此需要移除alluxio-runtime-master中环境变量  `ALLUXIO_MASTER_HOSTNAME`

移除该环境变量后，dataset-controller 执行命令时，会使用svc dns来获得master地址。



## 污点容忍

中移环境存在大量污点，控制面工作负载需要手动容忍污点，或者通过 `- operator: Exists` 容忍所有污点
